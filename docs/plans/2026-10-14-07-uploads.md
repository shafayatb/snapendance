## Decisions

| # | Decision | Choice |
|---|----------|--------|
| U1 | Batch model | One **open** batch collects captures. Submitting freezes it as **queued** in one transaction, only when it has items; a repeated tap finds no open batch with items and does nothing. The next capture opens a new batch. Batches and items use SQLite integer IDs ("Batch 15"); an item's ID is its stable idempotency key. |
| U2 | Storage | Database `uploads.db` (`sqflite`, schema version 1, `onUpgrade` from the start). Images under the app documents directory, `captures/IMG_yyyyMMdd_HHmmss_SSS.jpg`, copied from the plugin's temporary file, which is then deleted. JPEG as the camera produces it (`veryHigh`), not re-encoded. Order: copy, then insert; a failed insert deletes the copy; a failed copy inserts nothing. Images are kept after upload (thumbnails of synced rows). |
| U3 | Startup reconciliation | A file with no row is deleted (a crash between copy and insert). A row whose file is gone and not uploaded becomes **failed** with "Local file missing". An expired claim is left for the engine (U5). |
| U4 | Item states | `pending`, `uploading` (claimed), `retrying` (transient failure, attempts < 5), `uploaded`, `failed` (permanent, or the 5th transient failure: "Failed after 5 attempts · last: timed out"). Every attempt counts, including "no network", as task 08's criterion says; real offline time burns no attempts because the worker waits for a network (U8). |
| U5 | Engine | `SyncEngine.run()` claims **one item at a time** with one `UPDATE … WHERE id = (SELECT …)` statement (queued batch, `pending`/`retrying`, or `uploading` with an expired claim), a random claim token, and a 2-minute expiry (longer than the 30 s timeout). Outcomes are written only `WHERE claim_token = ?`. No transaction is held during an upload. A run tries each item at most once and stops early after a "no network" failure. Returns whether retryable work remains. |
| U6 | Mock API | `UploadApi.upload(item)` with `MockUploadApi` scenarios: success; fail once then succeed (fails when the item's stored attempts are 0, so it is deterministic and survives restarts); timeout (never answers; the engine's 30 s timeout fires); no network; permanent failure. The scenario lives in a `settings` table of the same database, so the background isolate reads it. Short simulated latency (~600 ms). |
| U7 | Progress and backoff | Completion only: "UPLOADING" with no percentage (the mock sends no bytes; deviation U1). No engine-owned next-attempt time, so no countdown (deviation U3). Backoff is WorkManager's exponential, 30 s initial. |
| U8 | Scheduling | `workmanager`: unique one-off work `upload-queue`, network-connected constraint, exponential backoff; policy `append` (or `appendOrReplace` if the plugin offers it) so a batch submitted during a run gets a later run. Enqueued on submit, manual Retry, app start and resume when unfinished items exist, and connectivity regain. A 15-minute periodic task (same constraint) is the documented recovery path. The worker returns `false` (retry with backoff) while retryable items remain, else `true`. The foreground never runs the engine itself. |
| U9 | Cubits | `CameraCubit` (existing) gains `takePicture()`. `BatchCubit` (uploads, provided app-wide): open-batch count and last thumbnail, pending count (Home H2 and the cloud badge), capture-in-progress, submit, one-off notices, and the mock scenario for the C11 sheet. The shutter calls `batchCubit.capture(cameraCubit.takePicture)`, so neither Cubit holds the other. `UploadsCubit`: the Upload Manager. The repository exposes a `changes` stream for writes in this isolate. While the Upload Manager is open it polls every 2 s, and it reloads on resume, so it sees writes from the background isolate. |
| U10 | Upload Manager | Batches with any item not uploaded, newest first. Unfinished rows are shown, and synced rows collapse into "n synced in this batch" (deviation from U1's one synced row). Overall card: uploaded/total over the shown batches. Failed: **Retry** resets attempts to 0 and status to pending, then enqueues. Missing file: **Remove** deletes the row. No Pause All. Thumbnails: `Image.file` with `cacheWidth` at display size. |
| U11 | Connection pill | `connectivity_plus`. OFFLINE when there is no connection (unfinished items show "WAITING FOR CONNECTION"). CONNECTED · UPLOADS FAILING when connected and the most recent attempt (`last_attempt_at`) failed. Otherwise STABLE LINK. A hint only, never proof of Internet. |
| U12 | Pending count | Items of queued batches that are not uploaded (failed included), matching "PENDING UPLOADS (n)". Home H2 shows "n images waiting" without the "· offline" part. |
| U13 | Simulation sheet | Shipped in release, labeled MOCK API (needed for the demo). |

## README notes (task 10 criterion, for task 11)

- Uploads run in a WorkManager job that needs a network connection. Android decides when it
  runs: usually within seconds of the network returning, but Doze, battery saver, and app
  standby can delay it, and after a failure the next try waits for exponential backoff (30 s,
  then longer). A 15-minute periodic job is a backup.
- Force-stopping the app (Settings → Force stop) cancels its scheduled work until the app is
  opened again; that is Android's rule for stopped apps. Swiping the app away from Recents
  should not cancel it on stock Android (not yet checked on the test phone; some vendors' battery
  managers do).
- Connectivity shown in the Upload Manager is a hint from the OS, not proof of Internet access.
- The upload API is a mock (MOCK API sheet from the camera's settings icon); scenarios persist
  across restarts and apply to background runs.
